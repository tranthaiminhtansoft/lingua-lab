1. Post-release checklist

ChecklistComplete when
☐ Workflow result
  • Verify deployed release: Success
  • Publish stable GitHub Release: Success
  • Production verification: all checks passed
☐ Release notes
  • Source branch matches the PRD Release run.
  • Include merged PRs from the previous stable tag through the current source commit.
  • List only changes verified against each PR diff.
  • Omit unchanged items, Summary, commit SHA, and production-verification status.
  • Preserve tag, title, target commit, and rollback assets.
  • Use the format below.
☐ Live spot-check
  • Open the Pages URL from the run.
  • Confirm the home page loads.
  • Open and refresh one route changed in this release.
  • Confirm the change is visible.

2. Edit the GitHub Release

  1. Open Lingua Lab → Releases, then open the stable release created by the successful PRD Release run.
  2. On the release page, select Edit release (pencil icon in the release card).
  3. In the edit form, keep the existing tag and title. Replace the content in Release description → Write with the notes format below.
  4. Select Preview. Check the source branch, PR links, and each listed change.
  5. Select Update release to save the notes.
GitHub fieldAction
TagKeep the existing release tag.
Release titleKeep the existing title.
Release descriptionReplace with the verified notes below; use Preview to confirm rendering.
Assets and release labelLeave unchanged.
SaveSelect Update release after reviewing the preview.

Release description format

## Source branch
release/homelab/YYYYMMDD

## PRs and changes

| PR | Changes |
|---|---|
| [#<number> — <title>](<PR URL>) | - <Specific feature, fix, CI/CD, or documentation change><br>- <Another concrete change, if applicable> |
| [#<number> — <title>](<PR URL>) | - <Specific change> |
  • List merged PRs from the previous stable tag through the release source commit.
  • Verify every bullet against its PR diff; omit unchanged items, a separate summary, commit SHA, and production verification status.
  • Keep each PR in one table row. Separate multiple changes with <br>-.

3. If a check fails

  • Stop release follow-up and consult the release owner.
  • Use the Rollback guide only when authorized.
  • Download production-verification only to inspect failed checks.
