Rollback and recovery

Start hereProduct guideReferenceProcedures

Use this standalone guide when an authorized operator decides production should return to a published stable release. A rollback dispatch is not proof of recovery.

  1. Open GitHub Actions and inspect recent PRD Rollback runs. If the failed release already automatically dispatched one, open that run; do not start a duplicate. Auto-dispatch occurs only when candidate deployment succeeded and verify_release failed, and still waits for human approval.
  2. If no suitable run exists and rollback is authorized, choose PRD Rollback → Run workflow, select master, enter release_version as the published stable YYYYMMDD version, then run it. The workflow resolves only a published non-draft/non-prerelease release with both retained assets and a valid checksum.
  3. Wait for Resolve requested stable GitHub Release. Read its summary and verify the exact release tag, URL, commit, and checksum-verified artifact match the intended target. Stop if wrong or unresolved; no deployment has happened yet.
  4. When prod approval is requested, review that target summary first. Click Review deployments, select/confirm prod, then click Approve and deploy (GitHub may label the final button differently). This is an explicit human decision.
  5. Wait for Redeploy selected stable release and Verify restored production site. Open the returned Pages URL, check the restored site, and read the final summary: only Rollback verified confirms both redeploy and verifier passed. Otherwise recovery is unconfirmed; escalate for a human decision.

If a failure happened before candidate deployment, no rollback is needed. For deployment failure, failed stable publication, or other ambiguous states, inspect live state and have the release owner decide; automatic rollback is not triggered for every failure. See the Release and Post-release guides.
