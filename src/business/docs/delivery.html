CI and delivery system

This guide describes configured repository workflows and recorded environment configuration. Workflow definitions do not establish that a particular run passed or that a production deployment is currently live.

Pull-request CI

.github/workflows/ci.yml is PR-only, targets master, and uses a changed-path allowlist. Eligible changes include the React app, language-home and shared code, test/public/E2E paths, root HTML/package/tooling configuration, and standalone operator docs. Changes limited to .github/** or scripts/** do not match the allowlist; changes under src/business/docs/** do. Repository policy and application validation are independent jobs; each starts from the PR event. The diagram shows configured jobs, not a successful run.

Branch protection caveat: a skipped path-filtered workflow can leave its check pending or skipped. Inspect the repository's current required-check policy; do not assume a skipped required check is satisfied or that path filtering provides a complete merge gate.

Release candidate and deployment path

  1. Run prd-create-release-branch.yml from master; it creates release/homelab/YYYYMMDD and dispatches PRD Release.
  2. PRD Release validates the branch/date, absence of a prior release and candidate SHA matching the protected master tip.
  3. Gate 1: approve the candidate before build.
  4. Build the pinned candidate, copy docs, stamp identity and retain the rollback archive/checksum plus a separate file-digest manifest. No lint, typecheck or tests run during build.
  5. Deploy through wc-release-pages.yml. Verify identity, every candidate file's SHA-256, direct routes/refresh, actual navigation, legacy redirect, docs/images/diagrams, JS/CSS errors and all 142 Kana glyphs. Speech controls use a simulated voice; audible playback requires a manual browser check. Download production-verification for results and failure screenshots.
  6. Gate 2: approve stable publication only after verification and the audible playback check pass.

Trust boundary: dispatch from trusted master. Candidate code runs after gate 1; inspect the pinned SHA, results and both approvals.

Rollback and recovery

prd-rollback.yml supports automatic dispatch after failed post-deployment verification and manual dispatch with a stable release version. Target resolution requires a published, non-draft, non-prerelease dated release, archive, and matching checksum. Following prod approval it redeploys the archive and verifies restored identity and representative routes. Its summary distinguishes verified recovery from unverified recovery requiring intervention. Dispatching rollback is not proof that recovery succeeded; a deploy failure or skipped verifier also requires careful status interpretation.

Approvals and serialization

Approval waits are not held in a workflow-level concurrency group, so a pending release approval does not block an emergency rollback approval. The actual release and rollback deployment jobs share the valid GitHub Actions concurrency group lingua-lab-production-deploy with cancellation disabled, which serializes Pages deployments without serializing human approval waits. GitHub keeps at most one pending run per group and may replace an older pending run; inspect queued deployment jobs and do not assume this is a durable FIFO queue.

Repository operational notes recorded required prod reviewer tranthaiminhtansoft and master-only policies for github-pages as read back on 2026-09-27. These are dated observations, not current evidence; re-read settings before a future release. Approval configuration does not mean approval was granted for any particular run.

Evidence and acceptance boundaries

Configured source

Workflow YAML and scripts describe intended automation and checks.

Run evidence

Inspect the exact head SHA, check conclusions, approval actor/time, and deployment verifier output.

Live evidence

Use the returned deployment URL to check served identity and route-specific content; HTTP success alone is insufficient.

Identity stamps and checksums have defined limits: a build stamp is not cryptographic proof of all served bytes, and archive/checksum stored together are not an independently trusted signature. Sampled routes do not prove the whole site. No production verification is asserted here.

Pull-request CI remains the merge control; release verification checks the deployed artifact.

Interactive delivery workflow

The retained Archify artifact represents configured release dependencies, not a transaction, guaranteed queue order, or live deployment observation. Its labels describe configured gates and do not assert a passing run.
