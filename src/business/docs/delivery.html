Pass and fail conditions

Application validation
  • ✓npm ci completes.
  • ✓Lint passes.
  • ✓Type checking passes.
  • ✓Unit tests pass.
  • ✓Pages-base build succeeds.
  • ✓Chromium, Firefox, and WebKit browser smoke checks pass.
Release Gate pass
  • ✓Trusted policy configuration is valid.
  • ✓When changed paths match the trusted allowlist, both current-head CI checks succeed within 25 minutes.
  • ✓When no changed path matches, the application CI wait is skipped.
  • Release Gate fail
    • Policy configuration is invalid.
    • PR head is stale.
    • Changed-file list is incomplete.
    • A required CI check fails.
    • The 25-minute wait expires.

The required status is Release Gate with strict up-to-date checking.

Configuration boundary: branch protection requires Release Gate, not the two application CI job names directly. The release gate reads the allowlist from the trusted PR base and checks results for the current PR head. A path-filtered skip can leave other checks skipped or pending; do not assume a skipped check satisfies a required status.

Release candidate and deployment path

Release Workflow
  • Releaser manually starts .github/workflows/prd-create-release-branch.yml on master.
  • The workflow creates release/homelab/YYYYMMDD and dispatches .github/workflows/prd-release.yml as a separate workflow run.
  • Release validation checks branch/date, tag uniqueness, and candidate SHA matching the protected master tip exactly.
  • After approval gate 1, build the candidate artifact and retained rollback archive. The release build does not run lint, typecheck, unit tests, or browser smoke tests.
  • Deploy through the reusable .github/workflows/wc-release-pages.yml workflow. Automation verification then checks the deployed site.
  • If post-deployment verification fails, PRD Release dispatches .github/workflows/prd-rollback.yml. If verification passes, approval gate 2 permits stable GitHub Release publication.
Automation Verification
  • Verify the deployed identity against the candidate SHA and compare every candidate file's SHA-256 with the candidate manifest.
  • Check direct route opens and refreshes, route-specific content, navigation, legacy redirect, docs/assets, and browser JavaScript/CSS failures.
  • The verifier runs the configured Grammar, Time, and Kana checks automatically after the deployed-site checks.
  • Kana speech controls use a simulated voice; audible playback is outside this automated verification.
  • The production-verification artifact retains the run report and failure evidence.

Rollback and recovery

  • Rollback may be dispatched automatically after a deployed candidate fails verification or manually with a stable release tag.
  • Target resolution requires a published, non-draft, non-prerelease dated release with a retained site archive and matching checksum.
  • After the prod approval gate, redeploy the retained artifact through the same reusable Pages workflow and verify restored identity/routes.
  • The workflow summary reports either verified recovery or unverified recovery requiring manual intervention.
