Follow the exact run in GitHub Actions. Do not approve based on a green-looking summary alone.

  1. Choose Create PRD Release Branch → Run workflow, select master, and run with no inputs. Wait for branch creation and automatic dispatch of PRD Release.
  2. Open that separate PRD Release run. Confirm it was dispatched from master and candidate_ref is the intended release/homelab/YYYYMMDD. Wait for source validation and candidate build; inspect pinned SHA and lint, typecheck, unit, browser, build, and retained archive/checksum evidence.
  3. Before the first approval, inspect all evidence above. At the prod gate click Review deployments, select/confirm prod, then Approve and deploy (the final button label can vary). Wait for Pages deployment and note its returned URL.
  4. Wait for Verify deployed release. Inspect its candidate identity and route results. If validation or build fails before deployment, no rollback is needed. If deployment succeeds and verify_release fails, the workflow attempts to dispatch PRD Rollback to the latest stable release—but that run still needs human prod approval. For deployment failures or any other failure state, inspect the live site and ask the release owner. Release failed? Open the Rollback guide; check whether a rollback run actually exists before acting.
  5. Only after successful verification, inspect verifier output and source identity before the second prod approval. Click Review deployments, select/confirm prod, then Approve and deploy. Wait for stable publication and inspect the final summary and GitHub Release URL.
  6. Continue with Post-release to visit the returned URL and spot-check routes. On any failure requiring recovery, go to Rollback guide.
